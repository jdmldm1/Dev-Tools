Key concepts subjects · wildcards · delivery

Everything in NATS is addressed by a dot-separated subject. Core NATS is fire-and-forget (at-most-once); JetStream adds storage, replay and acknowledgements (at-least-once, with optional exactly-once dedupe).

Subject wildcards

PatternMatchesDoesn't match
orders.us.newexactly thatorders.us
orders.*.neworders.us.new, orders.eu.neworders.us.west.new
orders.>orders.us, orders.us.west.neworders
>everything (debugging only)—

* matches one token; > matches one or more trailing tokens and must be last. Wildcards are for subscribing, never publishing.

Vocabulary

  • Queue group — subscribers sharing a group name split the messages; each message goes to one member.
  • Inbox — a unique reply subject (_INBOX.…) used by request–reply.
  • Headers — key/value metadata on a message (-H key:value).
  • Stream — JetStream storage that captures messages on a set of subjects.
  • Consumer — a cursor over a stream with its own position, filter and ack state.
  • KV / Object Store — APIs built on top of streams.
  • Account — an isolated subject namespace; $SYS is the system account.

Delivery guarantees

LayerGuaranteeSurvives no subscriber?
Core pub/subat-most-onceNo — message is dropped
JetStream + acksat-least-onceYes — stored and replayed
JetStream + Nats-Msg-Id + double ackeffectively exactly-onceYes

Reserved subject prefixes

$JS.API.>JetStream management API
$KV.<bucket>.<key>KV operations (stream KV_<bucket>)
$O.<bucket>.>Object Store (stream OBJ_<bucket>)
$SRV.>Service discovery (micro)
$SYS.>Server events and monitoring

Core pub/sub nats pub · nats sub

Publishers send to a subject; every matching subscriber gets a copy. Queue groups turn fan-out into load balancing.

Fan-out vs queue group

Publish

nats pub orders.new '{"id":1,"sku":"A12"}'
Publish a single message
nats pub orders.new "order {{Count}} at {{TimeStamp}}" --count 10 --sleep 500ms
Ten messages using built-in templates
nats pub orders.new "hi" -H "X-Trace:abc123" -H "Source:cli"
Add headers
cat event.json | nats pub orders.new
Body from stdin
nats pub orders.new "x" --jetstream
Publish and wait for a JetStream ack (stream must capture the subject)

Templates: {{Count}} {{TimeStamp}} {{Unix}} {{Random 10 100}}

Subscribe

nats sub orders.new
Print every message on a subject
nats sub "orders.>"
All subjects under orders. (quote wildcards in shells)
nats sub "orders.*.new" --queue workers
Join a queue group; run in two terminals to see load balancing
nats sub orders.new --count 5 --raw
Exit after 5 messages, print body only (pipe-friendly)
nats sub ">" --headers-only
Watch all traffic you're allowed to see, headers only

Request–reply nats request · nats reply

The requester publishes with a unique inbox as the reply subject and waits. Any responder on the subject answers to that inbox. Put responders in a queue group to load-balance them.

How it flows

Responder

nats reply svc.greet "hello from $(hostname)"
Answer every request with a fixed body
nats reply svc.echo --echo
Echo the request body and headers back
nats reply svc.time --command "date +%T"
Run a shell command per request; stdout is the reply
nats reply svc.time --command "date" --queue time-workers
Load-balanced responder (queue group)

Requester

nats request svc.greet "Jeff"
Send and print the first reply
nats req svc.time "" --timeout 2s
Short alias, custom timeout
nats req svc.ping "" --replies 0 --timeout 1s
Scatter-gather: collect every reply until the timeout
nats req svc.greet "hi" --count 100
Fire 100 requests (quick latency test)
No responders means nothing is subscribed to that subject — the server tells you immediately instead of waiting for the timeout.

JetStream streams nats stream …

A stream listens on subjects and stores what's published there. Retention decides when messages go away; limits cap size, count and age.

Stream → consumers

Each consumer keeps its own position, so one can lag, replay or filter without affecting another.

Create & inspect

nats stream add ORDERS --subjects "orders.>" --storage file --retention limits --max-age 7d --max-bytes 1GB --replicas 1 --defaults
Create non-interactively (omit flags to be prompted)
nats stream ls
List streams
nats stream info ORDERS
Config, message count, bytes, first/last sequence
nats stream report
Table of all streams with sizes and replicas
nats stream subjects ORDERS
Subjects stored and message counts per subject
nats stream edit ORDERS --max-age 30d
Change limits on an existing stream

Read & maintain

nats stream view ORDERS
Page through stored messages
nats stream get ORDERS 42
Fetch message by sequence number
nats sub "orders.>" --stream ORDERS --all
Replay everything via an ephemeral consumer (also --new, --last)
nats stream rmm ORDERS 42
Remove one message
nats stream purge ORDERS --subject orders.test -f
Purge one subject (drop --subject to purge all)
nats stream backup ORDERS ./backup/ORDERS
Back up to disk; nats stream restore to bring it back
nats stream rm ORDERS -f
Delete stream and its data

Stream settings that matter

FlagValuesMeaning
--retentionlimitsKeep until a limit is hit (default)
interestDelete once all consumers ack
workWork queue: delete on first ack; one consumer per subject
--discardold / newAt limit, drop oldest or reject new
--storagefile / memoryDurable vs fast
--replicas1, 3, 5Copies across a cluster
--max-msgs-per-subjectNKeep last N per subject (KV-like)
--dupe-window2mDedupe window for Nats-Msg-Id
nats pub orders.new "x" -H "Nats-Msg-Id:order-1001" --jetstream
Publish twice: the second is flagged as a duplicate and not stored

Consumers nats consumer …

Pull consumers let clients fetch batches when ready (preferred for workers). Push consumers deliver to a subject. Durable consumers have a name and survive restarts; ephemeral ones vanish when idle.

Create

nats consumer add ORDERS PROCESSOR --pull --deliver all --ack explicit --max-deliver 5 --wait 30s --filter "orders.new" --defaults
Durable pull consumer, redelivers up to 5 times if not acked within 30s
nats consumer add ORDERS AUDIT --pull --deliver new --ack none --defaults
Only messages from now on, no acks
nats consumer add ORDERS PUSHY --target orders.deliver --deliver last --ack explicit --defaults
Push consumer delivering to a subject

Consume & inspect

nats consumer next ORDERS PROCESSOR
Pull one message and ack it
nats consumer next ORDERS PROCESSOR --count 10
Pull and ack ten
nats consumer next ORDERS PROCESSOR --no-ack
Peek: it will be redelivered after the ack wait
nats consumer sub ORDERS PUSHY
Read from a push consumer
nats consumer ls ORDERS
List consumers on a stream
nats consumer info ORDERS PROCESSOR
Pending, ack floor, redelivered counts
nats consumer report ORDERS
Lag and ack pending for every consumer
nats consumer rm ORDERS AUDIT -f
Delete a consumer

Deliver & ack policies

--deliverStarts at
allFirst message in the stream
newMessages published after creation
lastThe last message
subjectLast message per subject
1000Sequence 1000
1hMessages from the last hour
--ackBehavior
explicitAck each message (use for work)
allAcking N also acks everything before it
noneNo acks; fire-and-forget read

Clients can also reply +NAK (redeliver now), +WPI (still working, extend timer) or +TERM (stop redelivering).

Key-Value store nats kv …

A bucket is a stream named KV_<bucket> keeping the last N revisions of each key. Keys use dots, so you can watch with wildcards.

Buckets

nats kv add CONFIG --history 5 --ttl 24h --replicas 1
Create bucket keeping 5 revisions per key, values expire after 24h
nats kv ls
List buckets
nats kv ls CONFIG
List keys in a bucket
nats kv info CONFIG
Bucket config and size
nats kv rm CONFIG -f
Delete bucket

Read & write

nats kv put CONFIG app.theme dark
Set a value (creates a new revision)
nats kv get CONFIG app.theme
Value plus revision and timestamp
nats kv get CONFIG app.theme --raw
Value only, for scripts
nats kv create CONFIG app.lock "host-a"
Set only if the key doesn't exist (simple lock)
nats kv update CONFIG app.theme light 7
Compare-and-set: only if current revision is 7
nats kv del CONFIG app.theme
Delete (leaves a tombstone; history kept)
nats kv purge CONFIG app.theme
Delete and erase history for the key

History & watch

nats kv history CONFIG app.theme
All retained revisions of a key
nats kv watch CONFIG
Stream every change in the bucket
nats kv watch CONFIG "app.>"
Watch a key prefix
Under the hood, nats kv put CONFIG app.theme dark publishes to $KV.CONFIG.app.theme. You can nats sub '$KV.CONFIG.>' to see writes as they happen.

Object Store nats object …

For files and large blobs. Objects are chunked into a stream (OBJ_<bucket>), so size isn't limited by max message size.

Buckets & files

nats object add ASSETS --replicas 1
Create a bucket
nats object put ASSETS ./report.pdf
Upload a file (name defaults to the filename)
nats object put ASSETS ./build.tgz --name releases/v1.2.tgz
Upload under a different name
nats object get ASSETS report.pdf --output ./copy.pdf
Download

Manage

nats object ls ASSETS
List objects with size and modified time
nats object info ASSETS report.pdf
Metadata, digest, chunk count
nats object watch ASSETS
See uploads and deletes live
nats object del ASSETS report.pdf
Delete an object
nats object seal ASSETS
Make the bucket read-only

Services nats micro …

Services built with the NATS micro framework (Go, .NET, JS, Python, Java…) register under $SRV, so the CLI can discover them and read their stats.

Discover

nats micro ls
All running services and instance counts
nats micro info orders-svc
Endpoints, subjects, queue groups, metadata
nats micro stats orders-svc
Requests, errors, average processing time per endpoint
nats micro ping orders-svc
Ping every instance

Call an endpoint

nats req orders.create '{"sku":"A12","qty":2}'
Endpoints are plain request–reply subjects

Errors come back as headers Nats-Service-Error and Nats-Service-Error-Code; the CLI prints them with the reply.

Ops, monitoring & bench nats server · nats bench

Most nats server commands need a user in the system account ($SYS). Create a dedicated context for it.

Cluster health

nats --context sys server list
Every server: version, connections, uptime
nats server ping
Ping all servers with RTT
nats server info
Detailed info for one server
nats server report jetstream
JetStream usage and Raft leaders per server
nats server report connections --sort in-msgs
Busiest connections
nats server check jetstream
Monitoring-style health check (exit codes for Nagios etc.)
nats server check stream --stream ORDERS
Health of one stream's replicas

Watch & debug

nats events
Live connect / disconnect / auth-error events
nats traffic
Live view of message rates by type
nats server request connections --subject "orders.>"
Raw connz query filtered by subscription subject
curl -s localhost:8222/jsz | jq
HTTP monitoring endpoints: /varz /connz /subsz /jsz /healthz

Benchmark

nats bench sub test --clients 4 --msgs 1000000
Start subscribers first (separate terminal)
nats bench pub test --clients 4 --msgs 1000000 --size 512
Core publish throughput
nats bench js pub test --create --msgs 100000 --size 1KB
JetStream publish throughput (creates a bench stream)
nats bench service serve svc --clients 2
Pair with nats bench service request svc for request–reply latency
Bench flags changed between CLI versions. Check nats bench --help on your build.

Handy one-liners

nats sub "orders.>" --raw | jq .
Pretty-print JSON traffic
nats kv get CONFIG db.url --raw > .env.db
Pull config into a file
nats stream info ORDERS --json | jq .state.messages
Most commands accept --json for scripting
nats schema info io.nats.jetstream.api.v1.stream_create_request
Look up JetStream API schemas
